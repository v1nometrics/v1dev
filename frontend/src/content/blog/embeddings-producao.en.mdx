## TL;DR
- Vectors are a stable mathematical interface for semantic search and matching.
- Postgres + pgvector covers 80% of cases without adding "another database" to the stack.
- The trade-off is index tuning + quality metrics (recall/latency).

## Why vectorization (and not a generative LLM)?

Vectors are **discriminative**: you compare positions in space and make reproducible decisions.

LLMs are great for generation, but they bring variance and cost to tasks that are sometimes pure similarity.

<Callout type="note">
Vectorization turns text into fixed-dimension vectors. The "semantics" live in the vector's position in space.
</Callout>

## Postgres + pgvector

```sql
CREATE EXTENSION vector;

CREATE TABLE documents (
  id SERIAL PRIMARY KEY,
  content TEXT,
  embedding vector(384)
);

CREATE INDEX ON documents 
USING hnsw (embedding vector_cosine_ops);
```

<Callout type="tip" title="Performance">
HNSW (Hierarchical Navigable Small World) provides approximate search with high recall and low latency.
</Callout>

## Metrics that matter

| Metric | What it measures | Typical target |
|--------|------------------|----------------|
| p95 latency | Response time | < 100ms |
| Recall@K | Search quality | > 0.9 |
| Semantic drift | Domain change | Monitor |
| Cost | CPU/RAM/IO | Budget |

## When NOT to use pgvector

- **Very high volume** (>100M vectors): consider Pinecone, Weaviate, Qdrant
- **Real-time search with a hard SLA**: evaluate specialized solutions
- **Complex multi-tenancy**: may need sharding
